## SECTION 02 — 문제 정의와 근거

### 2.1 문제 배경과 현황
기존 내용 그대로 유지 (수정 불필요):

> 모바일 쿠폰(기프티콘, 카드사 혜택) 시장은 빠르게 성장하고 있으나, 발급되는 쿠폰의 절반 이상이 3개월 이내의 단기 유효기간을 가지고 있어 소비자 관리에 한계가 존재함. 이로 인해 인지하지 못하고 방치되는 쿠폰의 소멸 및 수수료 발생 규모가 매년 수백억~수천억 원에 달하며, 소비자는 매장 앞을 지나치면서도 혜택을 놓치는 실질적인 금전적 손실을 겪고 있음.

| 근거 ID | 근거 유형 | 출처/조사 방법 | 핵심 발견 | 문제와의 연결 |
|---|---|---|---|---|
| E1 | 정부기관 보도자료 | kca.go.kr | 피해구제 접수 건 중 '유효기간 경과'가 58.0%로 최대 비중 | 유효기간을 넘기는 사용자가 많음 |
| E2 | 국회제출 공식자료 | biz.sbs.co.kr | 카카오톡 선물하기 환불 수수료(낙전/소멸) 규모가 최근 5년간 1,200억~1,600억 원 | 특정 플랫폼만으로도 미사용 사례가 상당함 |

*(E3 행 삭제 — 추가로 확인 가능한 세 번째 출처가 없음. 양식 §00 안내: "불필요한 예시 행은 삭제")*

### 2.2 핵심 문제 진술문
기존 내용 유지:
> 다양한 경로로 수신된 모바일 쿠폰을 보유한 사용자는 쿠폰의 유효기간과 사용 가능 매장을 일일이 확인하기 어려워 사용 기한을 넘기거나 매장을 지나치면서 혜택을 받지 못하고 있다.

### 2.3 문제 원인과 결과
기존 내용 유지 (외부요인 항목이 실제로 C-15 설계 근거와 정확히 일치):
> 표면적 현상: 쿠폰 유효기간 만료로 인한 소멸 / 근본 원인: 쿠폰이 카카오톡 선물함·문자·카드사 앱·갤러리 등에 흩어져 있고, 현재 위치에서 쓸 수 있는 쿠폰을 조회할 방법이 없음 / 외부 요인: 지하·실내 매장의 GPS 오차 및 음영 지역

## SECTION 04 — 솔루션과 가치 제안

### 4.1 제안 솔루션

*(수정 — "백그라운드 GPS"·"푸시 알림 발송"은 1차 범위 밖. 실제 흐름으로 교체)*

> 사용자가 캡처한 쿠폰 이미지를 업로드하면 이를 정형 데이터(JSON)로 파싱하여 DB에 저장한다. 이후 사용자가 전송한(또는 브라우저가 조회한) GPS 좌표를 기준으로 반경 300m 내 매장을 탐색하며, 사용 가능한 쿠폰이 있는 매장에 대해 RAG(브랜드별 예외 조건 검색) + Gemini(자연어 브리핑 생성)가 결합된 응답을 화면에 표시한다. **백그라운드 자동 감지·푸시 발송은 2차(안드로이드) 과제로 명시적으로 이관했다(C-2, C-16).**

| 구분 | 현재 방식 | 제안 서비스 | 개선 기대 |
|---|---|---|---|
| 정보 탐색 | 갤러리·카카오톡 선물함을 일일이 열어 확인 | 캡처 이미지 업로드 한 번으로 자동 파싱 | 등록 시간 대폭 단축 |
| 판단·분석 | 매장 앞에서 사용 가능 여부를 직접 판단 | 위치 기준 쿠폰 매칭 + RAG 예외조건을 AI가 종합 제시 | 잘못된 사용 시도 방지 |
| 결과 활용 | 유효기간 경과 후 소멸되거나 매장을 지나침 | 위치 조회 시 매장 근처의 쿠폰을 즉시 확인 | 미사용 쿠폰 소멸률 감소 |

### 4.2 핵심 가치 제안

*(수정 — 과장된 수치 제거, 실측 가능한 표현으로)*

- Zero-Input에 가까운 등록 편의성: 캡처본 1~3장 업로드만으로 자동 등록 (실측 파싱 시간: 1장 9초 / 2장 11초, §5 성능 요구사항 3초는 달성 못 해 15초로 목표 재조정, 이유는 §12 참고)
- 근거 기반 브리핑: "사용 가능합니다" 같은 단정 대신, 확인된 규칙이 있을 때만 반영하고 없으면 정직하게 "확인된 정보 없음"으로 안내
- 맥락 인식 브리핑: "143m 앞 스타벅스 아주대점, 아이스 카페 아메리카노 쿠폰이 29일 남았어요" 같은 실제 생성 문장(§8 예시)

### 4.3 대표 사용 시나리오

*(수정 — 안드로이드 백그라운드 감지 → 웹 클라이언트 흐름으로)*

1. **쿠폰 등록**: 카카오톡 선물하기 캡처 이미지를 웹 페이지에 업로드 → Gemini Vision이 브랜드·유효기간·바코드 추출 후 저장 (202 응답 후 비동기 처리, 폴링으로 결과 확인)
2. **위치 조회**: 사용자가 브라우저 위치 권한을 허용 → 좌표를 서버로 전송
3. **AI 브리핑 수신**: "143m 앞 메가MGC커피 아주대점이 있어요. (ICE)아메리카노 쿠폰이 있네요." 같은 문장을 화면에서 확인
4. **현장 결제**: 카드 상세 화면에서 마스킹된 바코드 정보로 매장 확인 후 결제 (바코드 원문은 저장하지 않음, C-11)

### 7.1 전처리·검증 규칙

- **브랜드 정규화**: `config/brands.json` 단일 출처 + Gemini enum 분류(1차) + 별칭 문자열 매칭(2차 폴백) — 표기 변형(예: "메가엠지씨커피"/"MEGA MGC COFFEE")을 하나의 `brand_id`로 수렴 (C-7, C-8)
- **좌표 처리**: 배열로 받되 최신 유효 좌표 1건으로만 매칭 (C-13). 좌표별 필터 5종 — 범위 초과(422 거절), 형식 오류(폐기), 정확도 100m 초과(폐기), 10분 이상 과거(폐기), 직전 좌표 50m 이내(DB 갱신만 생략)
- **중복 제거**: `client_upload_id`(같은 업로드 시도 방지, UNIQUE 제약) + `barcode_hash`(같은 쿠폰 재등록 방지, 부분 UNIQUE 인덱스)
- **단위·시간대**: 전 컬럼 TIMESTAMPTZ UTC 저장, 조회 시 KST 변환. Cloud SQL 인스턴스 타임존은 UTC로 고정
- **유효성 검사**: PostgreSQL 네이티브 ENUM 대신 TEXT+CHECK 제약 채택(값 추가 시 ALTER TYPE 부담 회피) — coupon_type, store_type, rule_type 등

### 7.2 데이터 모델/ERD

```
users 1 : N coupons  (FK, ON DELETE CASCADE)
coupons N : N stores (via brand_id, FK 없음 — 논리적 조인 키)
coupon_rules 는 brand_id/store_type으로 논리적으로만 연결 (FK 없음, RAG 인덱스라 생명주기가 다름)

users(uid PK, last_location geometry, last_location_at, fcm_token, ...)
coupons(coupon_id PK, uid FK, brand_id, coupon_type, product_name, face_value,
        expires_at, usage_note, barcode_masked, barcode_hash, status, ...)
stores(store_id PK, brand_id, store_name, geom geometry(Point,4326), store_type, source, ...)
coupon_rules(rule_id PK, content, embedding vector(768), brand_id, rule_type, store_type,
             source_name, verified_by, ...)
```

### 8.1 핵심 프롬프트

**F-01 파싱 시스템 프롬프트 (발췌 — 전문은 `app/services/gemini.py`의 `SYSTEM_INSTRUCTION`)**
```
당신은 한국 모바일 쿠폰(기프티콘) 이미지에서 정보를 추출하는 파서다.
1. 이미지에 실제로 보이는 글자만 사용한다. 추측하거나 지어내지 않는다.
2. 읽을 수 없는 항목은 반드시 null로 둔다.
...
8. brand_id는 정해진 브랜드 목록에서 정확히 하나를 고른다. 확신이 없으면 UNKNOWN.
   비슷해 보인다는 이유로 다른 브랜드를 고르지 않는다 — 틀린 코드는 사용자를
   엉뚱한 매장으로 보내지만, UNKNOWN은 아무 피해도 주지 않는다.
10. usage_note: 이 쿠폰에 적힌 제한 문구만 옮긴다. 같은 브랜드의 다른 쿠폰에도
    똑같이 적용된다고 확대 해석하지 않는다.
13. is_same_coupon: 확신이 없으면 true로 두지 말고 false로 한다 — 잘못 합친
    쿠폰은 사용자를 엉뚱한 매장으로 보낸다.
```

**F-03 브리핑 시스템 프롬프트 (발췌 — 전문은 `BRIEFING_SYSTEM_INSTRUCTION`)**
```
1. 100자 이내 한두 문장. 존댓말, 광고 문구처럼 딱딱하지 않게.
3. "확인된 규칙"이 비어 있고 usage_note도 없으면 사용 가능 여부를 단정하지 않는다.
5. verified가 false인 규칙은 "~일 수 있어요" 같은 완곡한 표현만 쓴다.
6. usage_note는 이 쿠폰 한 장의 조건이다. "이 쿠폰은"으로 한정하고 브랜드
   전체로 일반화하지 않는다.
```

| 테스트 ID | 대표 입력 | 기대 결과 | 실제 결과 | 판정/개선 |
|---|---|---|---|---|
| P-01 | 메가MGC커피 쿠폰 2장(상단+선물정보 화면) | 병합된 JSON, product_name+expires_at 동시 확보 | 성공, 파싱 11초 (2026-08-10 실측) | 통과 |
| P-02 | 1장만 업로드(선물정보 화면 없음, 컴포즈커피 아메리카노 상단 화면) | REQUIRED_FIELD_MISSING + "선물 사용 정보 화면도 함께 올려주세요" 안내 | 실측 확인(2026-08-11, curl) — `status:FAILED, error_code:REQUIRED_FIELD_MISSING`, message: "유효기간을(를) 읽지 못했습니다. 직접 입력해 주세요. 카카오톡 선물하기라면 '선물 사용 정보' 화면도 함께 올려 주세요." | 통과 |

### 8.2 환각·안전·오류 대응

- **근거 없는 답변 방지**: RAG 검색 결과가 비어 있으면(유사도 0.6 미만 포함) "확인된 정보 없음"으로 처리하고 사용 가능 여부를 단정하지 않는다(§8.6 원칙, 전 프로젝트에서 반복 적용 — C-14, C-15, C-21, C-23도 같은 원칙의 다른 적용 사례)
- **부적절한 입력**: 쿠폰이 아닌 이미지는 `NOT_A_COUPON`, 서로 다른 쿠폰이 섞인 다중 업로드는 모델 판정(`is_same_coupon`)과 서버 재검증(`per_image` 비교) 2단 안전장치로 `MULTIPLE_COUPONS` 처리 (C-14) — 등록 실패가 오알림보다 싸다는 판단
- **API 장애**: Gemini 호출 실패·타임아웃은 `UPSTREAM_UNAVAILABLE`(503)로 매핑. 브리핑 생성만 실패하면 TEMPLATE 폴백으로 서비스는 계속 응답
- **출력 파싱 실패**: `response_schema`로 구조를 강제하고, 스키마 위반 시 1회 재시도 후에도 실패하면 `PARSE_FAILED`

### 9.1 RAG 처리 흐름

```
매장 접근 감지 (brand_id, store_type 확보)
    ↓
① SQL 사전 필터: WHERE brand_id IN (:brand, '_common') AND store_type IN (:type, 'NORMAL')
    ↓
② 벡터 검색: ORDER BY embedding <=> :query_vec LIMIT 3   (코사인 거리)
    ↓
③ 유사도 임계값 컷: 0.6 미만이면 "관련 규칙 없음"
    ↓
④ Gemini에 근거로 전달 → 브리핑 생성 (source_name 함께 노출)
```

/locations 흐름은 고정 질의문 하나("이 매장에서 이 쿠폰을 사용할 수 있나요? 사용이 제한되는 조건이 있나요?")를 프로세스 생애주기 동안 1회만 임베딩해 재사용한다 — 매장마다 다른 문장을 지어 임베딩해도 실제 검색 좁히기는 ①번 SQL 필터가 담당하므로 얻는 게 없기 때문. `/rules/search`(단독 시연용)는 사용자가 입력한 질의를 매번 임베딩한다.

### 10.1 가장 큰 기술 위험과 대응

- **Gemini Vision 파싱 속도**: 실측 1장 9초/2장 11초로 초기 목표(3초) 미달 → 목표를 15초로 재조정하고 사유를 문서화(멀티모달 추론 특성). 폴링 예산 30초 안에 들어와 기능상 문제는 없음
- **PostGIS 반경 검색 단위 함정**: `geometry`에 그냥 `ST_DWithin`을 쓰면 미터가 아니라 도(degree)로 해석되어 지구 전체가 반경 안에 들어옴 → `::geography` 캐스팅 + 캐스팅 표현식 인덱스로 해결, `EXPLAIN ANALYZE` 0.155ms 실측 검증
- **다중 이미지 오병합**: 서로 다른 쿠폰이 섞여 저장되면 위치 알림이 엉뚱한 브랜드로 나감 → 모델 판정(`is_same_coupon`)과 서버 재검증(`per_image` 비교) 2단 안전장치 (C-14)

- **RAG 근거 없는 확답 위험**: 검색 결과가 없거나 부족한데 "사용 가능합니다"라고 답하면 실제 피해로 이어짐 → "확인된 정보 없음" 원칙을 코드 전반에 강제(§8.6)

### 15.1 시연 시나리오

1. **준비**: 로컬(또는 배포 URL)에서 웹 페이지 접속, Cloud SQL Auth Proxy 기동 확인
2. **입력**: 메가MGC커피 쿠폰 캡처 이미지 업로드 → 202 응답 → 폴링으로 COMPLETED 확인 (약 10초)
3. **화면 전환**: 위치 권한 허용 → 아주대 좌표(37.2803, 127.0433)로 위치 전송
4. **기대 출력**: 스타벅스 아주대점(143m) + 메가MGC커피 아주대점(207m) 두 매장이 거리순으로 표시, 각각 Gemini가 생성한 브리핑 문장
5. **설명 포인트**: *(수정 — 2026-08-11 RAG 규칙 교체 후)* 메가MGC커피는 실제 이용약관 규칙이 걸려 있어 이 화면에서도 `rules`에 근거가 채워져 나온다. 반대로 컴포즈커피는 아직 등록된 규칙이 없어 `rules:[]`(확인된 정보 없음)로 정직하게 나오는 대비를 보여줄 수 있다 → 추가로 `/rules/search`를 brand_id=starbucks, store_type=DEPARTMENT_STORE로 호출해 스타벅스카드 충전 제한 조항이 실제로 검색되는 것도 보여준다
6. **실패 시 대체 화면**: Gemini 브리핑 생성이 실패하면 `generated_by:"TEMPLATE"` 폴백 문장이 대신 나오는 것 자체가 "장애에도 서비스가 안전하게 계속 응답한다"는 설계 포인트이므로, 실패해도 대체 시연으로 쓸 수 있음

### 15.2 기술 선택 설명

| 선택 | 이유 | 검토한 대안 |
|---|---|---|
| Vertex AI + ADC (AI Studio API 키 대신) | 학교 GCP 프로젝트가 Vertex Express 모드라 `generativelanguage` 엔드포인트가 403으로 막힘(C-1) | AI Studio API 키 — 실제로 막혀서 폐기 |
| Cloud SQL 직행 (로컬 Docker 생략) | Windows Home + WSL2 세팅 리스크가 4일 일정에 부적합, 배포 환경과 동일한 곳에서 개발(C-5) | 로컬 Docker PostgreSQL |
| pgvector (FAISS 대신) | `WHERE brand_id=...` 같은 메타데이터 필터를 SQL 그대로 쓸 수 있음, Cloud Run(stateless)과 궁합이 좋음(DB_SCHEMA §8.1) | FAISS — 사전 필터가 번거롭고 다른 브랜드 규칙이 섞일 위험 |
| FastAPI + 원시 SQL (ORM 없이) | 스키마가 이미 `init.sql`에 확정돼 있어 ORM 매핑이 이중 관리 지점만 만듦 | SQLAlchemy ORM 모델링 |
| 웹 클라이언트 (안드로이드 대신, C-2) | 심사자가 설치 없이 배포 URL 접속만으로 검증 가능해야 함 | 안드로이드 네이티브 — 2차로 이관 |

### 15.3 예상 질문과 답변

| 질문 | 답변 |
|---|---|
| RAG가 틀린 답을 하면 어떻게 하나요? | 유사도 0.6 미만이거나 검색 결과가 없으면 "확인된 정보 없음"으로 처리하고 사용 가능 여부를 단정하지 않는다. 미검증(`verified_by=null`) 규칙은 브리핑 문장에서도 완곡 표현만 쓴다 |
| 개인정보는 어떻게 보호하나요? | 바코드 원문은 어디에도 저장하지 않는다(마스킹값+SHA-256 해시만). 배포는 `AUTH_DISABLED=true`(단일 공용 계정) 상태라 실제 개인 쿠폰은 등록하지 않는 운영 규칙으로 한계를 상쇄한다 |
| 비용은 얼마나 드나요? | Cloud Run은 `--min-instances=1`(콜드 스타트 회피)로 상시 비용 발생, Cloud SQL db-f1-micro도 상시 과금 — 시연 종료 후 0으로 되돌릴 예정 |
| 확장성은 어떤가요? | RAG는 규칙 수십~100건 규모를 가정한 설계(순차 스캔)라 브랜드가 크게 늘면 HNSW 인덱스 전환이 필요. `stores`/`coupons` 매칭 쿼리는 GIST 인덱스로 이미 0.155ms 실측 확인 |
| 사용자에게 실제로 가치가 있다는 근거는? | 파싱·매칭·브리핑의 기술적 동작은 실측했으나, "사용률이 실제로 늘어나는가"는 사용자 테스트를 하지 못해 검증하지 못했다 — 정직하게 후반기 과제로 남긴다 |
